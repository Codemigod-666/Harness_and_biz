How the harness works

Your setup for running several Claude Code agents on one project: a supervisor that plans, workers that build in parallel, and two subscription seats (A and B) sharing the load. Read a section at a time.

What this is

The harness is everything around Claude Code that turns one chat into a small team.

herdr

The terminal workspace. Every agent runs in its own herdr tab, and herdr's API lets one agent start, prompt and read the others.

devkit

Your Claude Code plugin in ~/dev-playbook/devkit: the skills (supervise, work, brief, land, handover, resume, fleet, backlog, conventions) and the context-guard hook.

fleet

The command that spawns, briefs, resets and lands workers. Each worker gets its own git worktree, branch, test port and account.

Accounts A / B

Two seats from the same organization. A is your normal login; B lives in its own config folder. fleet spreads workers across both.

All state lives in files (backlog, decisions, handovers, briefs, reports), never only in an agent's memory. That is what lets an agent be cleared, restarted, or moved to another account and carry on.

The big picture

You talk to the supervisor. The supervisor talks to workers through fleet. Work lands on main only after it is verified.

Green boxes run on account A, blue on B. Which worker gets which account is decided at spawn time: you pick with -a, or fleet picks the logged-in account running fewer agents.

Install and init

devkit is a Claude Code plugin that works in any git repo, on any stack. Two commands install it, one adopts a repo.

From GitHub (any machine)

/plugin marketplace add Codemigod-666/Harness_and_biz
/plugin install devkit@harness
# then, in your repo:
devkit init

devkit init detects the stack (justfile, Makefile, package.json, go.mod, pyproject, Cargo.toml, a Frappe app), proposes the check, test and gate commands, and adds .devkit/config.env, AGENTS.md, the docs/ tree (fleet roles, backlog, handovers, conventions) and a .gitignore line. It never overwrites a file. devkit doctor checks the setup; devkit check | test | gate run what the config says, so the skills never name just, go or pnpm.

From a local checkout (this machine)

~/dev-playbook/install.sh links devkit and the packs into ~/.claude/skills and the commands into ~/.local/bin, so edits in the checkout apply at once.

Accounts A and B

Two seats from the same organization, on one machine, kept apart by one environment variable.

How the separation works

Claude Code keeps its login, settings and history in a config folder: ~/.claude by default. The documented variable CLAUDE_CONFIG_DIR points it at another folder. So:

  • A is plain claude, with CLAUDE_CONFIG_DIR unset, using ~/.claude.
  • B is claude with CLAUDE_CONFIG_DIR=~/.claude-b.
Never set CLAUDE_CONFIG_DIR=~/.claude for A. When the variable is set, Claude Code keeps its global state inside that folder instead of ~/.claude.json, so A would lose its trusted folders and onboarding state. The tools always unset it for A.

What B shares with A, and what it keeps to itself

Item in ~/.claude-bShared?Why
settings.json, settings.local.jsonlinked to ASame permissions, hooks and auto-mode setup.
skills/, plugins/, hooks/linked to Adevkit and the herdr agent-state hook work the same on both.
projects/<project>/memorylinked to AAgents on A and B remember the same things about the project.
.credentials.jsonB's ownB's login. Never copied or linked.
sessions, history, .claude.jsonB's ownSeparate session history; B asks to trust each folder once.

Scoped to the project

B is never switched on globally. A project opts in with .claude/accounts.env (~/frappe has one). claude-acct a|b only starts inside a herdr pane, inside such a project. fleet sets the account on each worker's pane just before claude starts. Outside herdr, plain claude stays on A everywhere.

When one seat hits its limit

fleet respawn <name> -a b (or -a a): the worker commits a handover, exits, restarts in the same worktree on the other account and resumes. Nothing is lost, because the work lives in git and files. Both seats belong to one org, so an org-wide spend cap, if your admin set one, still applies to the total.

Log in to account B

A one-time setup. About five minutes.

  1. Get B's seat ready. Your org admin assigns a seat to B's email in the admin console. Accept the invite email and sign in once at claude.ai as B, so the seat is active.
  2. Check B's folder exists. Already done for frappe. To repeat it: 
    cd ~/frappe
claude-acct setup        # creates ~/.claude-b and the shared links; safe to rerun
  3. Prepare the browser. Your browser is probably signed in to claude.ai as A. Open a private/incognito window for the next step, or sign out of claude.ai first. Otherwise the browser silently approves the login as A.
  4. Sign B in. 
    claude-acct login b --email <B's email>     # add --sso if your org uses SSO
    It prints a URL. On WSL the browser may not open by itself: copy the URL into the private window, sign in as B, choose your organization, and paste the code back into the terminal if it asks.
  5. Verify. claude-acct status should show B with "loggedIn": true and B's email, and fleet accounts (inside a repo) should show b yes.
  6. First run. In a herdr pane in ~/frappe: claude-acct b. Approve the "trust this folder" dialog once. The /status command inside Claude shows which account is active.
Logged in as the wrong account? CLAUDE_CONFIG_DIR=~/.claude-b claude auth logout, then repeat steps 3–5. This only touches B; A stays logged in.

A working session

What happens when you say "go".

  1. Open the workspace. cd into the repo, run herdr, then just supervisor (or claude) in the first pane.
  2. Plan. The supervisor turns your goal into backlog items, each with a Goal and a Done-when. backlog ready lists what can start.
  3. Spawn. fleet spawn one -l "src/feature/**" creates worktree ../repo-one on branch fleet/one, a herdr tab, a test port and an account, then starts Claude in auto mode.
  4. Brief. fleet brief one .claude/fleet/briefs/T-012-one.md; the worker runs /devkit:work and stays inside its lane.
  5. Report. The worker ends with REPORT <path>. The supervisor checks Done-when against the diff and reruns the gate.
  6. Land. fleet land one fast-forwards main. fleet close one removes the tab and the merged worktree.

Context seams

Long sessions don't degrade. Each agent restarts itself from a file, on purpose, before its context fills up.

  1. 200k tokens: the context guard asks the agent to write docs/handovers/<name>.md, commit it, and say HANDOVER <sha>.
  2. 250k tokens: the guard blocks the agent from stopping until the handover is done.
  3. Reset: fleet reset <name> sends /clear, then /devkit:resume. The agent re-reads its handover, checks it against git, and continues.

The same handover is what makes respawn work across models and accounts.

Zip and Zap

Type "Zip" and the Frappe workspace goes safely into git and ~/frappe is emptied. Type "Zap" and it comes back exactly as it was.

The idea

~/frappe is a git repo. Git keeps what you write: custom apps, docs, settings. The bench in mybench/ (Python env, Frappe itself, assets, logs) is about 1.2 GB that can always be rebuilt, so it isn't saved; only its exact versions are, in .zip/bench.lock.json. Each site's data travels as one encrypted file in .zip/sites/.

Saved by ZipRebuilt by Zap
Custom apps, with historyFrappe at the same commit
Database, public and private files, the original site_config.json (encrypted)Python environment and Node packages
Bench settings: ports, developer mode, app orderBuilt assets, Redis config, Procfile
Claude memory and .zip/HANDOVER.mdLogs (not kept)

Zip, step by step

  1. Handover. Claude writes .zip/HANDOVER.md: where things stand and what's next.
  2. Checks. The bench must be stopped. Every file not in git must be on the "rebuildable" list, otherwise Zip stops and names the file.
  3. Lock and backup. Exact versions are recorded. Each site is backed up with its files and an exact row count per table, then encrypted with the key in ~/.config/frappe-zip/key.
  4. Push. Commit, tag zip-YYYYMMDD-HHMMSS, push.
  5. Prove it. A fresh clone from GitHub must match, and every backup must decrypt, match its checksum and contain a valid dump. If anything fails, nothing is deleted.
  6. Safety copy. A git bundle and the backups go to ~/.cache/frappe-zip-last/ for 7 days.
  7. Wipe. The site databases are dropped and ~/frappe is emptied.

Zap, step by step

  1. Clone the repo into the empty ~/frappe and read the lock.
  2. Rebuild the bench with bench init, pin Frappe to the locked commit, put the custom apps back, install requirements.
  3. Restore each site from its decrypted backup, with the original site_config.json, so encrypted passwords still work.
  4. Prove it. Row counts must equal the Zip's counts, table by table. Then build, migrate, ping each site, and check that the git tree is clean.
  5. Resume. Memory is put back, then Claude reads the handover and carries on.

How long

Zip took about 8 seconds in the rehearsal. Zap is estimated at 12–20 minutes the first time on a machine and 8–12 minutes when the pip and yarn caches are warm. Almost all of that is bench init and the asset build. This page gets the measured numbers after the first full rehearsal.

Keep the key safe. ~/.config/frappe-zip/key decrypts every backup. Keep a copy in your password manager: a new machine needs it, plus the MariaDB root password in ~/.config/frappe-zip/db_root.

Glossary

Supervisor
The one agent you talk to. Plans, briefs, verifies and lands; doesn't build features itself.
Worker
A separate Claude Code process in its own herdr tab and git worktree, working one backlog item.
Lane
The file globs a worker may change. Lanes never overlap, so workers don't collide.
Brief
A file telling a worker its goal, Done-when, lane, what to read and which model to use.
Done-when
The checkable conditions that define "finished" for a backlog item.
Gate
devkit gate: every check and test the project configures. Must be green before work lands.
Seam
A planned context reset: handover → clear → resume.
Auto mode
Claude Code's permission mode where a classifier approves safe actions and blocks risky ones. Never bypass mode.
CLAUDE_CONFIG_DIR
The environment variable that picks which config folder (and so which account) Claude Code uses.
